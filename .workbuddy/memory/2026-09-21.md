## 本机处理速度实测（用户要求"检测一下处理速度"）
- 新增 `scripts/bench_pipeline.py`（按真实流水线分阶段计时 + `nvidia-smi` 采样）
  与 `scripts/bench_report.py`（出速度分解图/表）；报告 `SPEED_BENCH.md`。
  **用独立 tag 跑，不碰正式产物**；GPU 侧同时记录功耗墙与降频原因。
- 实测（RTX 4060 Laptop 8GB，852×480@30fps，2203 帧）：

  | 阶段 | 每帧 ms | 备注 |
  |---|---|---|
  | decode 读帧 | 1.03 | 971 fps（纯解码） |
  | stabilize | 0.10 | track_frames |
  | detect YOLO26s@640 | 21.07 | GPU 利用率 43%，显存 821MB，29.6W |
  | **seg SAM@512** | **50.04**（热）/ 78.41（冷） | GPU 42.5%，1076MB，36.3W |
  | seg SAM@1024 | 143.05 | GPU 57.4%，1479MB，54.0W |
  | angle_mask | 2.41 | 纯 CPU |
  | **端到端** | **74.67（热）/ 103.02（冷）** | 13.4 / 9.7 fps；1024 为 167.34（6.0 fps） |

- 纯模型（`bench_sam2.py`，240 帧段）：512 载入 25.9 + 传播 23.6 ms（**40.2 fps**，1093MB）；
  1024 载入 52.9 + 传播 91.6 ms（11.1 fps，3516MB）。**两项之和与整段实测对得上**（49.5≈50.0、144.5≈143.1），
  所以分解可信。
- **核心结论：瓶颈不在 GPU。** 利用率只有 42%~57%、功耗 36~54W（墙 63~80W、硬件上限 140W，
  出厂默认 55W）。**@512 时 CPU 侧 JPEG 帧载入（25.9ms）与 GPU 传播（23.6ms）各占一半** ⇒
  只优化 GPU 收益封顶 ~25%。另外**抽帧那一步值 62.5s/全片**（冷热之差 78.41→50.04 ms/帧）。
- 实时性：30fps 需 ≤33.3ms/帧 ⇒ 当前慢 2.2 倍（热）/3.1 倍（冷）。但本项目是**离线分析**
  （73.4s 视频跑 165s），完全够用；实时约束只在机载时才成立。
  优化建议 ROI 排序：①消 JPEG 往返 ②YOLO 降频 ③流水线并行 ④编译/TensorRT ⑤提功耗墙（收益小）。
- 踩坑：
  * **`nvidia-smi` 文本别用定长窗口解析**：`SW Power Cap` 行有 35 个空格对齐填充，
    取 `[1][:40]` 会把 `Active` 截成 `Acti` ⇒ 误判成"未限功耗"。按行取 `:` 后的值。
  * **1024 对比忘了 `--det-source`** ⇒ `rocket_seg.py` 去找 `dets_bench1024.json` 抛
    `FileNotFoundError`，整段 3.3s "跑完"，差点当成"1024 更快"。已给 bench 脚本加 `--det-source`。
  * **同一命令冷/热抽帧差 36%**（帧缓存命中与否），混在一起会得出"速度不稳"的错误结论。
  * 机器状态影响很大：同一份 seg 代码，上一轮 126s、本轮冷跑 172.7s / 热跑 110.2s。
    **比速度必须同条件同时测，别跨天对比。**
